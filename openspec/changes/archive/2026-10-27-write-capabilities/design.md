# Design: Write Capabilities & Content Management for BookStack MCP

## Context
See `proposal.md` for motivation.
`mcp-bookstack` currently implements `BookStackClient` and `BookStackServer` using `rmcp` (v3.7) over stdio. The BookStack REST API documented in `.tmp/docs.json` provides standard RESTful endpoints for CRUD on pages, chapters, books, and shelves.

## Goals / Non-Goals

**Goals:**
- Provide full CRUD capabilities for pages, chapters, books, and shelves via standard MCP tools.
- Deliver robust safety guards preventing accidental or unauthorized deletions.
- Keep tool input schemas strictly compatible across all MCP hosts and LLMs using portable JSON Schemas (`anyOf` for nullable fields).
- Maintain Markdown as the first-class format for page content and tool outputs.

**Non-Goals:**
- Direct file attachments or image uploads via multipart form data (excluded in this iteration; handled separately if needed).
- Role or user permission administration (focus is on documentation content).
- Full BookStack recycle bin restoration/purging tools.

## Decisions

### 1. Dual Safety Guard for Deletions
- **Decision**: Require both a global server configuration flag (`BOOKSTACK_ALLOW_DELETE=true`) AND an explicit argument (`confirm: true`) on deletion tools.
- **Rationale**: LLMs can trigger tools autonomously. In BookStack, deletions send entities to the recycle bin, but restoring requires administrative UI access. A server-level flag ensures environments where delete is unsafe can turn it off completely, and `confirm: true` prevents inadvertent tool invocations.
- **Alternatives Considered**:
  - *No delete tools*: Restricts users from cleaning up temporary pages or restructuring content.
  - *Only parameter confirmation*: Risk of LLMs hallucinating `confirm: true` without human intent.

### 2. Markdown Preference with HTML Fallback
- **Decision**: Accept either `markdown` or `html` in `create_page` and `update_page`, mapping directly to BookStack's respective request fields.
- **Rationale**: Markdown is the natural idiom for LLMs and MCP clients. BookStack natively converts Markdown to page content, but existing workflows might submit HTML snippets.
- **Alternatives Considered**:
  - *Markdown only*: Breaks compatibility with BookStack instances configured with strict HTML templates.

### 3. Portable JSON Schemas via Schemars Attributes
- **Decision**: Use explicit `#[schemars(schema_with = "...")]` helpers returning `{"anyOf": [{"type": "..."}, {"type": "null"}]}` for all optional tool parameters.
- **Rationale**: Many MCP clients and LLMs strictly reject JSON Schema arrays `type: ["string", "null"]` generated by default by `schemars 1.x`.

## Risks / Trade-offs

- **[Risk] BookStack API Validation Failures (e.g. missing parent ID)** → Pre-validate required mutual dependencies in tool handlers (e.g., verifying that either `book_id` or `chapter_id` is supplied) before dispatching HTTP calls.
- **[Risk] Network / Permission Errors** → Capture BookStack HTTP error response body and surface actionable error messages in tool error output.
- **[Risk] Accidental Content Overwrites** → `update_page` accepts optional fields, allowing selective field updates without wiping out unaffected content.
